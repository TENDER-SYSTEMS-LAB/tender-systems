# Q-001 — A Shared Design System Across Systems

## Question

Whether TENDER SYSTEMS should maintain one design discipline governing every system it operates, and if so, what governs what.

## Why it matters

The institution operates more than one system and expects more. A shared discipline is exactly the kind of cross-system material this repository holds, while each system's own visual language stays canonical in its Lab repository.

## What the source contains

The user asked one question, quoted verbatim:

> "https://github.com/dickwu/apple-design-skill 여기에 있는 애플 디자인 스킬을 사용해서 우리의 작품들에 적용하면 좀 별로일까?"

The assistant answered that adopting the external skill wholesale is likely wrong, while using some of its principles as a lower layer is worthwhile, quoted verbatim:

> "그 스킬을 그대로 적용하는 건 오히려 별로일 가능성이 높고, 일부 원칙만 하위 레이어로 사용하는 건 상당히 좋다고 봐."

It proposed a precedence order placing institutional principles above project design language above per-system rules above external human-interface guidance above an accessibility and usability check, so that unconventional design triggers the question of whether the deviation is intentional rather than being corrected automatically. It also proposed two principles in English — that clarity is not the same as simplicity, and that intentional friction must not be automatically repaired. It closed by proposing a shared design skill governing current and future systems.

## Status of the proposal

The conversation ends on that proposal with no user reply of any kind. Nothing here is confirmed, deferred, or rejected by the user; all of it is `llm-proposed`. No such design document exists.

## Open sub-questions

- Whether a shared design discipline is wanted at all.
- What belongs to the institution versus to a system.
- Whether external human-interface guidance sits underneath institutional principles or is not used.
- How a rule against automatically repairing intentional friction would be applied in practice.
